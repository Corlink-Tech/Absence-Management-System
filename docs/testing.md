# برنامه آزمون و معیار پذیرش

در آغاز تحلیل هیچ کد یا آزمون قابل اجرا برای محصول مستقل وجود نداشت؛ بنابراین هنوز نتیجه آزمونی گزارش نمی‌شود.

## لایه‌های آزمون

| لایه | پوشش لازم |
|---|---|
| Unit دامنه | انتقال وضعیت، مانده، idempotency، date conversion شمسی/میلادی، policy و مرز سال |
| API integration | validation، auth/CSRF، pagination، فیلتر، خطا و OpenAPI schema |
| مجوز/امنیت | matrix نقش‌ها، IDOR، tenant/company isolation، داده پزشکی، export و فایل مستقیم |
| هم‌زمانی | تأیید/لغو/اصلاح رقابتی، رزرو روزها و اجرای هم‌زمان Job |
| Frontend | RTL، فرم، تقویم شمسی، خطا/loading/empty، مجوز UI و رفتار موبایل |
| Import/Export | dry-run، ردیف معیوب، rollback اتمیک، encoding فارسی و formula injection |
| عملیات | نصب پاک، migration، restart، worker، SMTP اختیاری، backup/restore واقعی |
| دسترس‌پذیری | صفحه‌کلید، focus، screen reader نام‌گذاری، contrast و کاهش حرکت |

## سناریوهای پذیرش P0

1. نصب روی محیط پاک بدون Nextcloud و راه‌اندازی حساب مدیر مستقل.
2. کارمند درخواست معتبر ثبت کند؛ رکورد و رزرو مانده واقعاً در PostgreSQL ثبت شود.
3. مدیر همان شرکت تأیید کند یا با دلیل رد کند؛ مدیر نامرتبط نتواند.
4. HR غیبت نیابتی ثبت و اصلاح کند؛ رویداد قبلی باقی بماند.
5. لغو/اصلاح تأییدشده مسیر تأیید مجدد داشته و مانده دقیقاً یک‌بار اصلاح شود.
6. تغییر شناسهٔ درخواست/کارمند/پیوست/شرکت به دسترسی غیرمجاز منجر نشود.
7. نوع محرمانه در API، تقویم، اعلان، گزارش، export و log به نقش غیرمجاز نشت نکند.
8. شمسی در ورودی و خروجی به تاریخ ISO صحیح تبدیل شود؛ سال کبیسه و مرز روز آزمون شوند.
9. تغییر مانده با دلیل، actor و before/after ثبت شود؛ عملیات تکراری double count نسازد.
10. API دارای OpenAPI و تست خودکار مجوز و ورودی نامعتبر باشد.

## دروازه‌های انتشار

برای هر مرحله، فرمان‌های واقعی lint/typecheck/test/security اجرا و نتیجه ثبت می‌شود. انتشار عملیاتی نیازمند آزمون migration از نسخه قبلی، backup encrypted، restore در محیط جدا، آزمون worker و تأیید انسانی HR/امنیت/IT است. تستی که به علت نبود سرویس اجرا نشد، «موفق» گزارش نمی‌شود. معیار بار، SLA و حجم داده پیش از استقرار توسط مالک سامانه تعیین شود.
